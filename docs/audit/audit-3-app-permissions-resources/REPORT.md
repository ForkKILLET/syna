# Independent audit, third round follow-up — Hyla-mini application: permissions, isolation and resources

Auditor: fresh-context adversarial pass (2026-09-05). Source under audit: commit `32d212a98f8e919d06a3d03f8f7d11d076a05295` (`main`, clean tree). Probes ran against the built copy `apps/hyla-mini/dist` (mtime 1788637412, newer than every source file it was built from; the third-round symbols `releaseReservation`, `newestLiveRecord`, `rehypeSanitizeFinalPass` are present in it) on Node v26.0.0, macOS (Darwin 25.2.0), filesystem backend only.

## Scope and method

Line: `apps/hyla-mini/src/site` (manager, worker, HTTP + static server, static builder), `src/render` (pipeline trust policy, sanitizer role, pipeline cache), `src/domain/site-config.ts`, `src/auth`, `src/app.ts`, `docs/HYLA_MINI.md`, `docs/PLUGIN_AUTHORING.md`, with the third-round ledger entries I-66…I-84 / D42…D53 as the primary attack surface.

Method: every source file above was read in full before any probe was written (comments were treated as claims, not facts); hypotheses were formed from the code and the documents' claims; each one was then reproduced or refuted with a standalone probe in this directory (`p01`…`p09`, style of `work/v05/probes/review-3-2026-09-05`: import from the built app and the test harness, print `PASS`/`FAIL`, exit 1 on any `FAIL`). Every probe's output is kept next to it as `<probe>.log`. Temporary directories were created with `mkdtemp` and removed; `apps/hyla-mini/work/` was never created; no PostgreSQL was used; nothing outside this directory was written. As a sanity check the shipped `render.test.mjs` and `audit-app.test.mjs` were run from the repository root on the same build (`shipped-tests-sanity.log`: 27 tests, 27 pass) — they pass on exactly the build where the probes below fail, which measures the coverage gap rather than a stale build.

Run everything: `for p in work/v05/audit-3/app-permissions-resources/p*.mjs; do node "$p"; done` (about 30 s).

### F-AP3-01 in detail

The R3 tests (`render.test.mjs:166`, `audit-app.test.mjs:620`) place the recipe's own `sanitize` stage with its default options (`finalPass` defaults to `false`, `factories.ts:143`), so the recipe's pass is `rehypeSanitize` and the appended pass is `rehypeSanitizeFinalPass` — two identities, two passes, and the appended one is last. The option is, however, part of the factory's public schema ("Run as an additional pass even when the recipe already used rehype-sanitize earlier (builder use)") and a stored recipe may set it. Then both the recipe's stage and the appended stage call `processor.use(rehypeSanitizeFinalPass, schema)`; unified's `addPlugin` finds the earlier attacher with the same function and replaces its settings in place (`node_modules/unified/lib/index.js:1157-1170`). The repeated-plugin guard in the builder (`pipeline.ts:167`) does not see it because (a) the appended stage is exempted (`!appended`) and (b) it compares `pluginId`, whereas unified compares the plugin function. The threat model is exactly the one D48 names — a third-party rehype factory admitted through `extraServices` after the recipe's sanitizer — and the probe's evil factory is the R3 fixture verbatim. A tenant does not need to be malicious: any recipe author who reads the option's description and sets it "to be safe" disables the platform's guarantee for their comments. The `stages` diagnostics report the appended stage as last, so an operator inspecting `BuiltPipeline.stages` would be told the guarantee holds.

### F-AP3-07 in detail

D33 made a closing record keep its unit until the close settles (correct: capacity bounds live Envs). The side effect nobody tested is what an acquirer of that record's key does meanwhile. `newestLiveRecord` excludes `disposing` (`manager.ts:241`), so the acquirer falls into the "drain others / `records.get(key)`" branch, finds the disposing record, skips creation (`:439`, the record is not `disposed`), skips the creating-join (`:469`), and at `:479-484` takes `continue`. The next turn starts with `readConfig()` — one store round-trip per turn, coalesced across concurrent acquirers of that tenant but not paced — until `records.delete(record.key)` runs in the disposal's `finally`. On the filesystem backend the probe measured about 10,000 reads per second from one acquirer; on PostgreSQL that is a query loop per closing tenant. Idle eviction (the sweeper, `evictIdle`, the release hand-over) is the normal trigger: a SiteEnv whose authenticator or context cleanup takes longer than `acquireTimeoutMs` makes that tenant answer 503 for the duration of every eviction. The fix is local: wait for `record.disposal` instead of re-reading.

### Notes on the remaining findings

- F-AP3-03: the probe shows the design property "a build never takes the last unit" holds; the defect is only the pointless eviction. Its cost scales with how often builds are retried (a scheduler retrying a refused build every few seconds keeps evicting whatever is idle).
- F-AP3-04, reasoning-only variant: if `shutdown()`'s `disposeRecord` ran while `boundSites.enter()` itself was still pending (`record.env` undefined, `manager.ts:271`), the disposal would resolve at once, the creator would later `await record.disposal` and rethrow (`:376-379`), and the entered Env would be closed by nobody until `runtime.dispose()`. `p04b-enter-window.mjs` measured `enter(SiteEntry)` at 0.09–0.20 ms and settling inside the microtask queue (no macrotask hop), so the window cannot be hit from outside the manager; it is left as a reasoning-only note (a defensive `await record.env?.dispose()` re-check in the creator's `record.disposal` branch would close it for free).
- F-AP3-05 is a documentation defect unless the timer is meant to be per wait; the doubled bound matters for HTTP clients only through the 503 latency.
- F-AP3-06 requires write access to the output directory (a planted or foreign manifest); it is listed because the documentation and the error code both promise a check that is not performed, and because the deleted files are, by the builder's own definition, not its own.

## Limits of this audit

- Filesystem backend only (by instruction); nothing here exercises the PostgreSQL store, pool or migrations. F-AP3-07's read loop is a query loop there, unmeasured.
- Timing-based probes (`p04`, `p05`, `p08`) carry this machine's numbers; the defects they show are structural (the code paths cited), not timing artefacts, but the exact counts will differ elsewhere.
- F-AP3-01 needs a rehype stage after the recipe's sanitizer that adds content — the same third-party-factory premise the R3 tests and D48 adopt. With only the shipped factories the merge still happens (the appended pass runs before `rehype-external-links`), but nothing in the shipped set adds dangerous content, so the observable harm needs `extraServices`.
- The static builder's check-then-write on symbolic links (`static-builder.ts:302-304`) has an inherent window between `lstat` and `mkdir`/`rename`; it is the documented boundary ("checked before the first write") and was not probed (it needs a local writer racing the build).
- `site-manager.test.mjs` (H11 heap sampling, minutes) and the matrix/PostgreSQL suites were not re-run; only `render.test.mjs` and `audit-app.test.mjs` were, as a sanity check of the build.
- No fuzzing of Markdown or of the recipe JSON beyond the cases above; Ajv schema validation of recipes/site configurations was read, not fuzzed.
- `docs/HYLA_MINI.md` and `docs/PLUGIN_AUTHORING.md` were checked claim by claim against the code for the sections in scope (工作集, 权限边界, 静态输出, 可信/不可信输入); the backend and delivery sections were not.
