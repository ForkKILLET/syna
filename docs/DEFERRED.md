# Deferred (v0.7)

Things noticed during the v0.6 API consolidation and the v0.7 round that were **not** changed, because they are outside the change list of the task book (命名) or because they would change behaviour beyond the three revisions of 0.7 (语义). Each entry says what was seen and where; none is a commitment, and none is on the 1.0 candidate surface (`docs/API_STABILITY.md`). The items the v0.7 round resolved — S1 (waiter deadline), S2 (`env.state` and the ledger), S6 (`FRESH_CONSTRAINT_FAILED` split), S7 (`INVALID_ENV_STATE` / `INVALID_DESCRIPTOR`), S8 (`MISSING_IMPLEMENTATION` shapes), S10 (`asSynaError()`) and N2 (the selector remnants) — are removed from this list; the numbering keeps its gaps.

## 命名 — names outside the list, left as they are

| # | Where | Observation | Kept because |
|---|---|---|---|
| N1 | `ImplementationDescriptor.persistentRef` | The task book suggested `ref`; `ImplementationCandidate` (which extends the descriptor) already has `ref: CandidateRef`, a different kind of reference (Phase A finding F1). | Two reference kinds must not share one field name on one object. `persistentRef` stays; only its type (`ImplementationRef`) and its key (`familyId`) changed (R5). |
| N3 | Error `details.site`, `details.deadlineMs`, `inspect().planCache.maxEntries` | R6 renamed only the policy-context field (`dependencySite`); M1 renamed only the options (`limits.setupDeadlineMs`, `limits.planCacheEntries`). Error details and inspection fields keep `site`, `deadlineMs`, `maxEntries`. | Outside the list, and the v0.5 snapshots pin these keys; renaming them would be a semantic-output change. |
| N4 | `benchmarks/v0.5-planning.mjs` case label `bound-entry-private-range-request-enter-dispose-100` | The case function and comment say `AnchoredEntry`; the result label keeps the 0.5 wording. | `scripts/benchmark-compare.mjs` matches cases by name against `benchmarks/results-v0.5.0-baseline-same-machine.json`; renaming the label would break the same-machine comparison the release depends on. |
| N5 | a name for `ServiceRef<T> \| InputRef<T>` | `DependencyRef<T>` — which in 0.6 meant this union and was deprecated — was removed in 0.7.0; `DependencyRefFor<D>` types the ref of a declared dependency. Whether the bare union deserves a name of its own is open. | No caller needs the union: `env.deps` is typed per dependency and `loadAll()` rejects Input refs structurally. Adding a name would be a public name outside the 0.7 task book. |
| N6 | `EntryCallArguments<E>` / `EntryRunCallArguments<E, Result>` | Module-level tuple aliases in `descriptors.ts` used by the `enter` / `run` overloads; not exported from the package entry. | M2 fixes the public names at `EntryParameters` and `EntryArguments`; exporting the tuples would add a public name outside the list. |
| N7 | `SynaError` is no longer a `class` | T1 makes `SynaError` a value (constructor) plus a union type; `class X extends SynaError` stops type-checking (nothing in this repository did it). | The task asks for a code-discriminated union; a class cannot be one. Recorded in the migration table. |

## 语义 — behaviour that looked wrong or improvable, left unchanged

| # | Where | Observation | Not done because |
|---|---|---|---|
| S3 | `provides: [primary(C)]` | A default-implementation declaration (the `@Primary` counterpart) would remove most `MISSING_AUTO_POLICY` cases. | 0.6 task book §3.6: no default implementations; the 0.7 task book names `primary()` among the things not to do (a new public name outside its change list). Still deferred: `MISSING_AUTO_POLICY` with an explicit `auto()` policy is the documented answer, and a default that a package declares for itself would let a dependency choose its supplier without the world saying so. |
| S4 | `C.all` coexistence | Every candidate is a real node of the current Env; a candidate whose setup fails still fails the collection's caller. | 0.6 task book §3.6; the 0.7 task book names the relaxation among the things not to do. Still deferred: a candidate that is not a real node would reintroduce the selector's pre-check (`availability`), whose last remnants 0.7 removed; failing the caller is the honest outcome of "every candidate is part of the topology". |
| S5 | New dependency forms, Entry capabilities, Runtime options | Including `ServiceFamily.range()` (Phase A finding F2): `serviceRange(revision, range)` took a **revision** as the range's origin; a Family-level `range()` would be a range without an origin and would change private-realm resolution (0.5 third round C1/C2). Also `load({ timeoutMs })`: a per-call wait shorter than `setupDeadlineMs`. | 0.6 task book §3.6; D4 deleted `serviceRange` and added nothing; the 0.7 task book names `ServiceFamily.range()` and `load({ timeoutMs })` among the things not to do. Still deferred: S1 made the deadline the waiter's, so `load({ signal: AbortSignal.timeout(ms) })` already is the shorter wait (`LOAD_CANCELLED`) without a second option for the same thing (naming guideline 4); a Family-level range still has no origin. |
| S9 | `C.all` version resolution with several active revisions | With both `1.2.0` and `1.9.0` of a family active in one Env, `set.resolve({ version: '^1.0.0' })` picks the highest satisfying version (`1.9.0`); the deleted selector picked the active-ancestor revision (`1.2.0`) because only one was active in its world. | This is `C.all`'s existing rule (v0.5 `defaultRuntimePolicy`), recorded in the migration table under D3; not a change made in 0.6 or 0.7 (the planning layer is unchanged in 0.7 by construction: reference planner differential and the 0.5 snapshots). |
| S11 | Cross-ancestor reuse | Ordinary reuse targets only the parent's currently visible slots (v0.5 §3); a slot an ancestor owned and the parent no longer sees is not searched for (Binding flip-back creates a new instance). | The 0.7 task book names it among the things not to do. Still deferred: 0.5 withdrew the historical-instance search deliberately (`docs/SEMANTIC_CHANGES_V05.md` §3, §9); the lineage anchor is the one persistent promise, and a wider search would change plans the snapshots pin. |
| S12 | Prepared / activation groups / any setup barrier | A way to enter an Entry before its owner is Ready, or to make un-awaited `load()`s hold a setup, keeps being asked for by callers who want a "prepared" world. | The 0.7 task book names Prepared and any barrier among the things not to do. Still deferred: 0.5 withdrew the activation transaction and the completion barrier (`docs/SEMANTIC_CHANGES_V05.md` §2); `OWNER_NOT_READY` and plain Promises are the model (K02/K07), and 0.7's S1/S2 rest on `load()` having no hidden obligation. |
| S13 | A generation-switching host (Runtime hot reload) | A host that swaps a Runtime generation under live Envs, migrating or draining them, would let a long-running process take new definitions without a restart. | The 0.7 task book names it among the things not to do. Still deferred: a Runtime is finite, closed and immutable (v0 core); generation switching is a host concern above it (Hyla-mini's site manager rotates SiteEnvs by configuration revision inside one Runtime), and nothing on the 1.0 candidate surface is needed for it. |
