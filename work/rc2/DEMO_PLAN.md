# rc.2 demo plan (DEMO_PLAN)

Task book: `work/tasks/SYNA_RC2_EXECUTION_PROMPT.md`. Seven runnable programs under `apps/01-*` … `apps/07-*`, one fictional domain, every demo asserting its own result (exit 1 on any failed assertion), its last stdout line `<name>: OK`, one gate step each (`demo-01-basics` … `demo-07-failure-modes`, `scripts/verify-release.mjs`, matching the stable lines listed below). Core untouched: everything uses the frozen surface of `docs/API_STABILITY.md` only.

## The domain: a multi-tenant notification delivery service

Four words — tenant, provider, notification, delivery — and their mapping onto Syna (the demos show the mapping, never a Syna concept as a business name):

| domain | Syna | where |
|---|---|---|
| a provider's client (credentials, a connection, a rate limiter) | Service, its resource closed by `onDispose` | `AcmeNotify` (1.8.4, 2.4.1), `GlobexNotify` (3.1.0) |
| "can send a notification" | Contract `Notifier` (`send(notification) → Delivery`) | `@syna-demo/notify-contract` |
| which provider a tenant chose | Binding `PreferredNotifier` + an `ImplementationRef` stored as JSON | `03`, `04`, `06` |
| the current tenant, the current notification | Inputs `CurrentTenant` (tenant-store), `CurrentNotification` (notify-contract) | `02` on |
| a daily digest job | a child world created by a Service through the `AnchoredEntry` it depends on | `05` |
| the provider SDK shipped a v2 | two Revisions of one Family admitted together | `04` |
| shared infrastructure nobody but its owner closes | `Logger` (eager), `TenantStore` (a fake connection pool) | `01` on |

## The seven programs (Phase C, one commit each)

Each demo: `apps/0N-<name>/` with `package.json` (`@syna-demo/0N-<name>`, `syna.id` `demo.examples.<name>`), `tsconfig.json`, `src/index.ts` (+ a domain file where it helps reading), `README.md` whose first paragraph answers the question without naming Syna internals, then "what the code shows", "run", "what it prints". `node apps/0N-<name>/dist/index.js`; `npm run demo:0N`; `npm run demo` runs all seven.

| demo | question | program | asserts | stable lines the gate matches |
|---|---|---|---|---|
| `01-basics` | how do I define services, connect them and enter a world? | inline `AcmeConnection` (a Service owning a fake connection, `onDispose` closes it) and `Dispatcher` (requires the connection and `Logger`); `Main` Entry; `runtime.run(Main, async ({ dispatcher }) => …)` delivers one notification | the delivery receipt; the connection opened once and closed after `run()`; the dispatcher did not open the connection before its first `deliver()` (`ServiceRef.load` is the trigger); the logger's lines in order; `liveEnvCount 0` | `01-basics: delivered welcome-1 via Acme (receipt acme-1)`, `01-basics: connection closed after the world ended: true`, `01-basics: OK` |
| `02-per-tenant` | each tenant gets its own instances, without a named scope | `AppEntry` (root: `TenantStore`, `Logger`; parameter `TenantStoreConfig`) → `TenantEntry` (parameter `CurrentTenant`; `reuse: { share: [TenantStore, Logger] }`); inline `Outbox` reads `CurrentTenant` and requires `AcmeNotify` (2.4.1); `app.explain(TenantEntry, …)` prints the new and forked nodes with their causes; two tenant worlds deliver one notification each; a call that asks for a fresh store under the `share` constraint is refused | the two outboxes and the two Acme clients are distinct (`input-provided` / `dependency-forked`), the store and the logger are the same instance in both worlds and in the root; `explain().services` counts; the refusal is `SHARE_CONSTRAINT_FAILED`; `liveEnvCount 0` | `02-per-tenant: tenant world: N new, M reused, forks: …`, `02-per-tenant: acme-corp and globex-fans use different Acme clients: true`, `02-per-tenant: OK` |
| `03-user-configurable` | let a tenant choose its provider and store the choice | `PreferredNotifier = define.binding('preferred-notifier', Notifier)`; a settings page built from `Notifier.all` (`candidates` → display name, version, `implementationRef`); the choice `PreferredNotifier.to(GlobexNotify)` written as JSON into the tenant's file by `TenantStore`, read back, `PreferredNotifier.parse()`d and passed as the `TenantEntry` Binding parameter; `Outbox` requires `PreferredNotifier` | the file holds exactly `{ kind: 'implementation-ref', contractId, familyId, range }`; parse round-trips; acme-corp delivers via Acme 2.4.1 and globex-fans via Globex 3.1.0; the settings page lists both providers; `liveEnvCount 0` | `03-user-configurable: settings page: Acme Notify 2.4.1, Globex Notify 3.1.0`, `03-user-configurable: stored choice for globex-fans: {"kind":"implementation-ref",…}`, `03-user-configurable: OK` |
| `04-two-versions` | v1 and v2 of one provider coexist; an old tenant's stored choice keeps working | `AcmeNotify` 1.8.4 and 2.4.1 admitted together (plus Globex); a choice stored before v2 (`range ^1.8.0`) resolves to 1.8.4, a new tenant's (`^2.4.1`) to 2.4.1; `catalog.implementations(Notifier)` and `catalog.revisions()` list them; an inline `Audit` service takes `AcmeNotify1.range('>=1.8.0')` and gets the Contract view of the newest compatible revision; a stored choice for a version nobody ships is `MISSING_IMPLEMENTATION` with `details.available` | the resolved versions per tenant; the catalog's three records; the range consumer sees 2.4.1 while the legacy tenant keeps 1.8.4; only the exact 2.4.1 reference exposes `sendBatch`; the error code and `available`; `liveEnvCount 0` | `04-two-versions: catalog: demo.notify.acme@2.4.1, demo.notify.acme@1.8.4, demo.notify.globex@3.1.0`, `04-two-versions: legacy tenant (^1.8.0) → Acme 1.8.4; new tenant (^2.4.1) → Acme 2.4.1`, `04-two-versions: OK` |
| `05-scheduled-jobs` | how does a service create typed child worlds by itself? | `DigestScheduler` (eager; requires `DigestEntry`, `TenantStore`, `Logger`; `check()`s the digest world during its own setup, opens nothing until the host calls `runOnce()` after the root is Ready) opens one digest world per tenant through the `AnchoredEntry` (`run()` with the world's own `DigestJob` Input), in parallel; each world's `DigestJob` reads its Input, uses the shared pool, and is gone when `run()` returns; a control shows that entering from inside setup is `OWNER_NOT_READY` | one child world per tenant, all sharing the root's pool id; distinct job instances; `liveEnvCount` back to 1 after `runOnce()`; the control's error code (`ENTRY_ACTIVATION_FAILED` with `causeCode OWNER_NOT_READY`); `liveEnvCount 0` at the end (absorbs `fluida-demo`) | `05-scheduled-jobs: digests sent: acme-corp (pool 1), globex-fans (pool 1)`, `05-scheduled-jobs: worlds alive after the run: 1`, `05-scheduled-jobs: OK` |
| `06-testing` | how do I replace the real provider in an integration test? | the 03 shape (Binding, `Outbox`, `TenantEntry`) built twice: `createRuntime({ services })` and `createRuntime({ services, overrides: [override(AcmeNotify, RecordingNotifier)] })`; `RecordingNotifier` records every `send()`; the same `deliverAll(runtime)` runs under both | the delivered notification ids and statuses are identical under both runtimes; the fake recorded exactly the calls the real one served; `inspect().overriddenServices` names the source; the Binding written for the real revision still resolves under the override; `liveEnvCount 0` | `06-testing: real and fake runtimes agree: true`, `06-testing: recorded calls: welcome-1, invoice-2`, `06-testing: OK` |
| `07-failure-modes` | what happens when setup fails, hangs, or the world closes? | five scenes, each its own Runtime with short limits and `diagnostics.onEvent` collected: (1) sticky failure — bad credentials fail once, every later `load()` gets the same error without a new attempt; (2) `failure: { attempts: 3, delayMs, afterExhaustion: 'retry-on-next-load', cooldownMs }` — a flaky provider; (3) `loadTimeoutMs` — a slow start: `LOAD_TIMEOUT` with `details.slot / elapsedMs / attemptStillRunning`, `attempt-overdue`, then the late success adopted (`attempt-succeeded-late`, `adopted: true`); (4) bounded close — a setup that never settles: `env.dispose()` returns after the grace, `env.state === 'disposed'`, `inspect().unsettledAttempts`, `attempt-abandoned` naming its dependencies, `runtime-attempts-outstanding`; (5) a setup wait cycle — `LOAD_TIMEOUT` with `details.suspectedWaitCycle`; every scene prints the code and the key `details` fields | the codes, the attempt counts, the event sequence per scene, the ledger contents, timings within the limits; `liveEnvCount 0` per scene | `07-failure-modes: sticky: LOAD attempts=1 …`, `07-failure-modes: retry: …`, `07-failure-modes: slow start: LOAD_TIMEOUT … adopted late: true`, `07-failure-modes: bounded close: disposed in ≤ grace, unsettled attempts: 1`, `07-failure-modes: OK` |

`02` and `03` are the two a reader sees first; the READMEs' example section is cut from them.
